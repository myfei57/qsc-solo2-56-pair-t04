# 凝露风险防护子系统（psdline.dew）

雨季门区玻璃起雾结露、司机看不清对位时，按门区温湿度与门体温差判定风险，
风险高时先把这樘门从批量开门里摘出，并安排擦拭；环境恢复后自动放开。采集、
门控、清扫、审计串成一条链，断线、漂移、部分失败都能扛住，历史不可变、可重放。

## 链路

```
环境采集 SensorMonitor        轮询三路（门区气温/相对湿度/门体玻璃温度）
  │                          断线、越界、跳变、卡死、冗余分歧/漂移 → 质量标签
  ▼
风险判定 RiskAssessor         纯状态机（无 IO），实时与重放共用同一份代码
  │                          OK / RISK / DARK，结论带完整证据
  ▼
门控联动 DewHoldRegistry      RISK/DARK 摘门（独立于联锁故障锁，原因分别上报）
  │                          door/batch.py 跳过被占用门区，记 skipped[group]="dew"
  ▼
清扫调度 CleaningPlanner      RISK→擦拭单 WIPE，DARK→人工核查单 INSPECT
                             派单失败自动重试；门区恢复取消在途工单
  ▼
不可变审计 EventChain          全部事实进 SHA-256 哈希链（分段 JSONL，fsync）
                             Replayer 校验链完整性并用同一状态机重建结论
```

## 两个关键取舍

### 1. 瞬时值还是趋势？——两者叠加，各司其职

* **物理线瞬时触发**：门体温度已低于露点（凝露余量 ≤ 0 ℃）当拍立即摘门，
  不等任何确认。安全优先，玻璃真到凝露点不能被平滑延迟。
* **趋势稳态触发**：指数平滑余量持续低于预警线达到确认时长才摘门，防抖动。
* **迟滞放开**：放开要余量持续高于更高的解除线、数据质量恢复 good、且无擦拭
  在途，并持续更长时间。摘门快、放开慢，避免在临界点反复开合。

### 2. 固定判据还是随季节调整？——物理线固定，运行线分季

* 判据建立在物理量（门体温度 − 露点温度）上，**凝露零线是自然常数，两季相同、
  不可放松**（配置校验禁止把它抬到零线以上）。
* 随季节切换的是**运行参数**：雨季预警线更高、确认更快、放开更慢；旱季相反。
  策略是版本化冻结对象（`std-1` / `rainy-1`），每次生效都把完整参数写进哈希链，
  事后重放按当时版本重建，今天调参改不动昨天的结论。

## 三种状态与失败处理（fail-safe）

| 状态 | 含义 | 批量开门 | 工单 |
|------|------|----------|------|
| `OK` | 数据可信且余量安全 | 放行 | 取消在途单 |
| `RISK` | 物理线触发或趋势确认 | 摘门 | 擦拭 WIPE |
| `DARK` | 必需量不可信（断线/越界/漂移坐实） | 摘门 | 人工核查 INSPECT |

* **断线**：驱动读不到值或超过 `stale_after_s` 无新数据 → `bad`；恢复后需连续
  健康 `requalify_s` 才重新参与判定（不拿黑暗后的第一拍就证明"安全"）。
* **漂移**：冗余通道持续分歧 + 分歧通道自身有累计跳变证据 → 坐实为 `bad` 并隔离；
  剩余健康通道继续供数（部分失败可运行），但融合结果降级，期间不自动放开。
* **真实气象变化不被误判**：单通道快速变化（来雨、车门贯入）仍可用，只是留痕；
  只有"快速变化 + 与冗余通道持续不一致"才坐实漂移。
* **DARK 不下"已凝露"结论**：`margin` 留空、置信度 `blind`，只派人核查探头，
  与真起雾的擦拭区分开。

## 不可变历史与重放

* 每条事件携带序号、时间戳、类型、负载与前一条的 SHA-256，删改任一条都会让
  从该点起的哈希全部对不上（`EventChain.verify`）。
* 入链内容：拓扑、策略版本、**每路原始采样与通道健康证据**、状态变迁及判定
  证据、摘门/放开、工单全生命周期。
* `Replayer.run()`：校验链 → 按链重建拓扑/策略 → 把历史采样喂回**与实时相同**
  的融合与判定状态机 → 与链上状态变迁逐条比对。
* `Replayer.explain(station, group)`：回答"当时凭什么报了风险"——策略版本、
  三路读数与质量、瞬时/平滑余量、触发原因、随后的摘门与擦拭记录。

## 对外接口

* 平台方法：`dew_sample / dew_cycle / dew_status / dew_replay / dew_explain /
  dew_report_wipe / dew_report_inspect / dew_report_failed`。
* HTTP：`GET /api/dew`、`GET /api/dew/replay`、`GET /api/dew/explain`、
  `POST /api/dew/sample`、`POST /api/dew/wipe-done`、
  `POST /api/dew/inspect-done`、`POST /api/dew/work-failed`。
* CLI：`psdline dew status|replay|explain`；`make demo` 含完整凝露场景自检。

生产接入时把 `POST /api/dew/sample` 的三个量换成真实采集服务的上报（湿度路
`null` 即代表该路断线）；把清扫派单网关（`DewSystem(dispatcher=...)`）接到班组
调度，返回拒收会自动重试。
